**Tout le chapitre tient dans ce schéma.** Les entrées sont immuables : logs bruts déversés tels quels, instantané des comptes exporté de la production (jamais interrogée par le job), petite table de catégories. Les tâches map enrichissent chaque événement avec la table diffusée (broadcast hash join), puis émettent par `user_id` ; leurs sorties triées locales sont téléchargées par les reducers (le shuffle), qui joignent chaque compte à ses événements grâce au tri secondaire (sort-merge côté reduce).

La sortie est une base **neuve** en fichiers triés. Les serveurs clé-valeur la chargent d'un bloc, basculent atomiquement et gardent la version d'hier : un bug se répare en rebasculant puis en relançant le job. C'est possible parce que rien n'a été modifié en place et que rien ne dépend d'une source vivante : ni cache écrit ligne à ligne, ni API interrogée pendant le calcul. Le workflow est déterministe, donc rejouable.
